## 八、第三方客户端接入设计

**背景**：租户已有既定运维工具链（Xshell / PuTTY / SecureCRT / mstsc / Navicat / WinSCP 等），强制更换工具是推行堡垒机的主要阻力。原文档仅有 FR-08-09「第三方客户端兼容」（P2，仅描述快捷键习惯）——**没有通道打通与监控保障的技术方案**，属真实缺口。

现已补齐（详设 6.6.5 共 9 个小节 + 规划 12.5 + 需求 FR-08-09 细化并升为 P1）：

| 接入模式 | 适用客户端 | 打通方式 |
| --- | --- | --- |
| SSH 网关模式 | Xshell / PuTTY / SecureCRT / 终端 | 直连堡垒机 SSH 端口，认证后进入资产选择 |
| SSH 跳板模式 | 同上（保留原命令） | 配置 ProxyCommand / ProxyJump，用户仍写目标地址 |
| 本地端口转发 | 任意 TCP 客户端（Navicat / DBeaver / WinSCP） | 经 SSH 建本地隧道，堡垒机识别内层协议后转代理 |
| RDP 网关模式 | mstsc / FreeRDP | 连堡垒机 RDP 端口，服务端渲染采集 |
| 数据库原生网关 | Navicat / mysql / psql | 直连堡垒机数据库端口，账号映射 + SQL 审计 |
| SFTP / FTP 网关 | WinSCP / FileZilla / scp | 直连堡垒机文件端口，目录白名单 + 文件审计 |
| 开放 API | 租户自研运维平台 | REST / gRPC 发起会话，同一代理链路 |

**核心原理**：堡垒机对客户端呈现为「标准协议服务端」——客户端以为在连资产，实际连的是堡垒机；堡垒机再用托管账号连真实资产，在代理层完成命令解析、录像与策略执行。

**监控保障**（不依赖客户端配合）：服务端协议解析、录像独立采集、凭证不落地客户端、协议层禁止反向转发、会话票据绑定、RDP 服务端水印、会话标注接入方式。

**必须明示的能力边界**：第三方客户端接入 = **审计完整性可保证，终端管控能力受限**。

| 能力 | 自研客户端 | 第三方客户端 |
| --- | --- | --- |
| 命令审计 / 阻断 / 录像 | ✅ 完整 | ✅ 完整（服务端实现） |
| 剪贴板精细控制 | ✅ 单向可配 | ⚠️ 仅协议层粗粒度 |
| 本地盘映射审计 | ✅ 支持 | ❌ 无法感知 |
| 防截屏 / 防复制 | ✅ 支持 | ❌ 不支持 |
| 客户端合规状态上报 | ✅ 支持 | ❌ 不支持 |

## 九、开放 API 接入的审计设计

**背景**：租户自研运维平台通过 API 接入时，最大风险是**审计断链**——平台用一个应用凭证调接口，堡垒机只看到「平台发起的会话」，无法定位到具体运维人员。原文档 FR-08-04 仅有「接口鉴权、幂等、调用日志」等笼统验收，未涉及操作人归属。

现已补齐（详设 6.6.5.7 共 5 个子节 + 需求 FR-08-04 细化 + **新增 FR-08-12「API 接入的操作人归属与审计」（P0）**）：

### 平台侧开发量分级

| 层次 | 改造内容 | 开发量 | 审计效果 |
| --- | --- | --- | --- |
| 零改造（配置级） | 仅把连接地址改为堡垒机，用户名携带资产标识 | 无需改代码 | 命令与录像完整 |
| 标准集成（推荐） | 认证 → 资产查询 → 申请票据 → 建立连接，并传实际操作人 | 约 3~5 个接口调用（3~5 人日） | 完整（含操作人、业务关联号、API 留痕） |
| 深度集成 | 增加任务下发、审计回传、事件订阅（Webhook） | 完整 SDK 集成 | 完整 + 双向可追溯 |

### 关键设计：实际操作人归属

**原则：API 只负责发起会话，授权判定与审计记录都以「实际操作人」为准，不以应用凭证为准。**

- 申请会话必须携带 `operator`（user_id / username / name），未携带默认**拒绝**
- 服务端**按操作人**判定资产授权与审批要求（不按应用凭证判定）
- 会话记录同时保存 `app_id`、`operator`、来源 IP、业务关联号（工单号/任务号）
- 仅纯自动化场景可开启「平台代操作」模式，且强制标记并告警

### API 接入下记录的操作

| 层次 | 记录内容 |
| --- | --- |
| API 调用层 | 调用应用、接口、参数摘要、结果、耗时、来源 IP |
| 会话层 | 会话 ID、应用标识、**实际操作人**、来源 IP、资产、账号、协议、起止时间、录像摘要 |
| 命令层 | 命令原文、时间、提权链路、命中策略、执行结果 |

## 十、客户端前置准入与录像实现（新增设计）

### 客户端前置准入（详设 **6.6.6 独立章节，11 个子节** + 需求 FR-08-13）

### 录像实现（详设 6.8.4）

核心结论：**录像是服务端代理层的能力，与客户端形态无关。**

| 会话类型 | 采集对象 | 数据形态 | 体积 | 回放 |
| --- | --- | --- | --- | --- |
| 字符（SSH/Telnet） | 完整 PTY 字节流 + 时间戳 + 窗口事件 | 带时间戳事件流（类 asciinema cast） | 1 小时 1~5 MB | 终端重放 + 文本检索 + 命令定位 |
| 图形（RDP/VNC） | 服务端解析显示通道并重建帧缓冲 | 编码视频（H.264/VP9） | 1 小时 50~200 MB | 视频回放 + 时间轴 + 关键帧 |

**关键设计：展示流与录像流分离** —— 展示流低延迟优先（可降画质），录像流完整性优先（不受客户端影响），二者互不干扰。

**跨接入形态一致**：自研客户端、第三方客户端、开放 API 三种形态的录像能力完全相同（均经代理采集）。

## 十一、图形桌面运维设计（RDP / VNC）

**问题**：被运维对象是远程桌面（Windows 桌面 / Linux 桌面）时是否支持？——RDP 已完整支持（P0），但 **Linux 图形桌面的接入方式原先没有说明，VNC 仅一行、缺实现设计**。现已补齐（详设 6.6.7 共 8 个子节）。

### 支持范围与接入方式选择

| 被运维对象 | 协议 | 推荐度 | 版本 |
| --- | --- | --- | --- |
| Windows 桌面 / 服务器 | RDP | ⭐⭐⭐ 首选 | V1.0 |
| **Linux 桌面 + XRDP** | RDP | ⭐⭐⭐ **首选** | V1.0（复用 RDP 链路，无需额外开发） |
| Linux 桌面 + VNC | RFB（VNC） | ⭐⭐ 备选 | V1.1 |
| Linux 桌面 + X11 转发 | X11 over SSH | ⭐ 不推荐 | 不支持（按隧道管控禁止） |
| NoMachine / SPICE | 专有 | 按需 | 项目专项适配 |

**Linux 图形桌面优先推荐 XRDP**：在 Linux 上装 XRDP 即可复用现有 RDP 代理链路，管控能力（剪贴板/驱动器/打印重定向）完整，实施成本最低。VNC 作为资产已部署 VNC 时的备选。

### 两种架构模式（按客户端形态自动选择）

| 维度 | 透传代理（MITM） | 服务端渲染 |
| --- | --- | --- |
| 原理 | 客户端与资产协商会话，服务端中间解密、转发并旁路采集 | 服务端作为 RDP 客户端连资产，重建帧缓冲后重编码推送 |
| 客户端要求 | 需原生 RDP 能力（Windows / Linux 客户端） | 任意客户端（含 Web 浏览器） |
| 性能 | 好（接近原生） | 服务端 CPU/GPU 开销大，时延略高 |
| 录像 | 解密后旁路采集显示通道更新 | 帧缓冲直接进入编码器 |
| 适用 | Windows / Linux 原生客户端（默认） | Web 客户端；需水印、强制降画质场景 |

### 透传模式的录像实现（关键）

三种方案取舍：**MITM 中间人解密（主方案）** / RDP 会话镜像（仅 Windows 备选）/ 客户端上报（仅 Web 辅助）。MITM 需客户端信任堡垒机 CA，时延增量 ≤ 30 ms。

### VNC 的能力差距（必须对客户说明）

| 能力 | RDP | VNC |
| --- | --- | --- |
| 剪贴板管控 | 完整（允许/禁止/单向） | 基础（依赖扩展） |
| 驱动器重定向 | 支持并可审计 | **不支持** |
| 打印重定向 | 支持并可审计 | **不支持** |
| 编码效率 | 高 | 中等（带宽占用更高） |

**VNC 场景下代理层强制加密**（VNC 原生弱加密不作安全边界）。

### 其他子节

- **6.6.7.5 审计增强**：图形录像"只能看不能搜" → 键盘输入记录、窗口标题事件、关键帧标记、OCR 辅助（可选）
- **6.6.7.6 性能与资源**：透传（低开销、带宽 1~5 Mbps）vs 渲染（CPU/GPU 高、并发为字符会话 1/5~1/10）；H.264 + 硬件编码（QSV/NVENC）
- **6.6.7.7 兼容性测试矩阵**：9 个维度（Windows/Linux 资产、RDP/VNC 客户端、4K 分辨率、多显示器、输入法、重定向、弱网）

## 技术要点

- **插图**：SVG 描述图形 → 无头 Chrome 渲染 2 倍分辨率 PNG（中文字体微软雅黑）。支持流程图、泳道图、UML 时序图、ER 图、状态机图、高保真界面原型。
- **单一数据源**：需求条数、优先级分布、设计章节映射集中在 `lib/reqdata.js`，由 `gen-reqdata.js` 自动提取；表 2-4/2-5、附录 A、表 9-1 均由它渲染，从机制上杜绝手抄不一致。
- **目录**：COM 调用 WPS 的 `TablesOfContents.Update()` 生成真实目录与页码。
- **表格**：所有行设置 `cantSplit` 防止跨页断裂；长文本列可指定左对齐自动换行。
- **中文字体**：每个文本运行显式设置 `eastAsia` 字体。
