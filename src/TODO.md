## 二、功能补全

- [ ] **UKey 证书：CRL / OCSP 吊销检查**
  现状：吊销判定以本库 `km_cert.status` / `revoke_time` 为**权威源**，这对
  内部 CA 场景是充分的 —— 证书由本系统签发，吊销也由本系统执行，
  引入 CRL/OCSP 只会多一份需要同步的副本。缺口在于**对接外部 CA**：
  对方签发的证书是否被吊销，本系统无从得知，只能靠管理员手工吊销本地记录。

  实施要点（若将来确需对接外部 CA）：
  - CRL：下载 → 解析 → **必须校验 CRL 的签发者 DN 与 `nextUpdate`**，
    并拒绝已过期的 CRL（把过期 CRL 当作"无吊销信息"处理）；
  - OCSP：构造请求时带 **nonce**，收到响应后 **必须验响应签名、验 nonce 回显、
    验响应者证书**。参考实现（svs-universal）正是把响应签名校验整段注释掉了，
    等于只解析状态码不验签，引入即是负资产，不可重蹈；
  - 刷新策略按 CRL 的 `nextUpdate` 定时，而非固定间隔；
  - 前置条件：先确认目标 CA 的证书里确实带 CRLDP（`2.5.29.31`）或 AIA
    （`1.3.6.1.5.5.7.1.1`）扩展 —— 实测本机那把 UKey 的证书**两者都没有**，
    对这种证书做 CRL/OCSP 是白做。

- [x] **UKey 证书：到期巡检与续期提醒** —— 2026-10-21：临期列表 API + 登录 hint；过期登录拒绝（原有）
  现状：`km_cert.not_after` 有值，但没有任何巡检。证书静默到期后，
  用户表现为"某天突然登录不了"，而错误信息只会说"证书校验失败"，
  排查方向被误导。需要：
  - 定时任务（如每日）扫描全部 `cert_type='client'` 且 `status='active'` 的证书，
    按剩余天数分档（如 30 / 7 / 1 天）产生待办；
  - 在证书链管理与用户证书界面显著展示"即将过期"，而不是等它过期；
  - 登录链路上，若所用证书将在 N 天内过期，在登录成功响应里带回提示
    （用户此刻正在用这把 Key，是最合适的提醒时机）；
  - 提醒渠道需先确认本项目有什么可用（通知表 `sys_notification` 之类的迁移
    是否已建、是否需要邮件通道）。

- [ ] **UKey 证书：自动轮换**
  现状：已具备完整的手工换发链路（用内部 CA 重新签发 → `DownloadSingleCert`
  灌回 UKey，且实测灌卡只替换 `iKeyType=2`、不破坏原证书），但需要人工触发。

  需要明确"自动化能走到哪一步"：**服务端签发可以自动化，灌卡不可能全自动**
  —— 写卡需要用户在场并输入 PIN。所以现实形态是"服务端按策略自动签发 +
  生成待灌卡任务 + 提示用户插入 Key 完成写入"，而不是无人值守轮换。
  另需考虑：轮换期间新旧证书的**并存窗口**（否则换发瞬间若灌卡失败，
  用户会被锁在门外），以及轮换失败的回滚。

- [ ] **UKey 证书：按证书粒度的准入策略**
  现状：证书经管理员登记绑定后即可用于登录，粒度只到"这张证书属于哪个用户"。
  可增强为按证书维度限制准入条件，例如：
  - 限定来源 IP / 网段（该证书只能在特定办公网使用）；
  - 限定时间段（只允许工作时间登录）；
  - 限定可访问的资产范围（这张证书只能运维某几台机器，
    与用户角色权限取交集而非并集）。

  关联：`acl_grant_rule`（ABAC 策略表）已存在但**决策逻辑未实现**（见本清单
  其它条目），证书级准入应复用同一套策略引擎，避免再造一套判定逻辑。

- [ ] **密码卡：pkcs11 Provider 的两个新签名方法仍是骨架**
  背景：为支持 RSA（内部 CA 的 SM2 链与 RSA 链并存），`crypto.Provider`
  接口新增了 `KeySignWithHash(ctx, keyID, data, h)` 与
  `KeySignPrehashed(ctx, keyID, digest, h)`。`soft` 实现已完成并有测试，
  **`pkcs11` 实现仍直接返回 `ErrNotImplemented`**。

  影响面：接入密码卡后，**RSA 签名路径不可用**；SM2 路径不受影响
  （仍走原有的 `KeySign`，语义未变）。实施时需按 PKCS#11 机制映射，
  例如 `CKM_RSA_PKCS`（对已摘要值签名）与 `CKM_SHA256_RSA_PKCS`（对原文），
  注意两者入参语义不同，与 `KeySignPrehashed` / `KeySignWithHash` 一一对应。
  与本清单"SDF Provider"那条一并考虑：设备提供 SDF 还是 PKCS#11 决定走哪条路。

- [ ] **命令策略：直接改库后需重启才生效**
  `PolicyService` 的引擎缓存只在**通过 API 修改策略**时失效（`invalidateEngine`）。
  运维若直接改 `policy_command` 表（如执行迁移），必须重启管理服务才生效；
  多实例部署时各实例缓存也不会互相通知。根治办法是引入 Redis 发布订阅
  或把策略刷新做成定时任务（服务端已有每分钟刷新，管理服务没有）。

- [ ] **命令策略：交互式解释器内的命令无法拦截**
  当前命令截获基于 pty 字节流的行缓冲，因此 `vim` 内执行 `:!rm -rf /`、
  `python` 内 `os.system(...)`、脚本文件内的命令都拦不到。
  这是启发式防线的固有边界，需要在产品说明与界面中明确提示；
  真正的兜底是会话录像 + 全量审计 + 网络准入。
  可增强方向：对进入交互式解释器的会话提升审计级别并告警。

- [ ] **密码卡 / 密码机接入（SDF Provider）**  ← 用户指定：暂缓，本轮不做
  背景：阶段 7 在目标服务器上发现其**本身就是一台密码机服务器**
  （`/opt/hsm/bin/ccit_tcp_server 9099`、厂商库 `/opt/hsm/libs/libsdf_crypto.so`、
  Tomcat 管理台 `/usr/local/ccit/server/cipher_machine_mgr`）。
  该设备对外提供的是 **SDF（GM/T 0018）接口**，不是 PKCS#11。

  实施要点：
  - 在 `src/shared/crypto/` 下新增 `sdf` 包实现 `Provider` 接口，
    通过 CGO 或厂商提供的 Go 封装调用 `libsdf_crypto.so`；
  - 保留现有 `pkcs11` 骨架（部分密码卡确实走 PKCS#11）；
  - 工厂 `factory.New` 增加 `provider=sdf` 分支与连接参数
    （设备地址/端口、密钥索引、PIN）；
  - `KeyGenerate/KeySign/KeyDecrypt/KeyEncrypt` 映射到 SDF 的
    `SDF_GenerateKeyPair_ECC` / `SDF_InternalSign_ECC` / `SDF_InternalEncrypt_ECC` 等；
  - 现有密钥元数据表 `km_key` 已按"密钥不出安全边界"设计，**无需数据迁移**：
    切换 Provider 后旧密文仍由 `soft` 后端解密，新数据走硬件；
  - 需要在真机上验证 SM2/SM3/SM4 与**二级密钥管理**（KEK/DEK）路径。

- [x] **凭据不托管模式（运维时手动输入资产口令）** —— 已实现并端到端验证

      实现：

        与 `require_approval`，并把唯一索引从「人+资产+账号」下沉到
        「人+资产+账号+grant_kind」——**绑定与通行证是两类记录，互不覆盖**；
      · 此前 `uk_grant` 只到账号维度，工单到期会把绑定关系一并改掉，
        也表达不了"绑定但访问要审批"，这是本次拆分要解决的具体问题；
      · 判定改为三态（`repo.EvaluateAccess`）：有效通行证 → 放行；
        绑定免审批 → 放行；绑定需审批但无通行证 → 拒绝且
        `need_approval=true`（提示"请提交工单申请"）；都没有 → "没有可用授权"。
        前两种拒绝必须区分：一个要提交工单，一个要找管理员要资源；
      · 需审批的绑定**仍出现在运维侧列表**（`/api/v1/ops/assets` 带
        `need_approval=true`），否则运维会以为没有这个资源；
      · 前端「访问授权」页增加"访问时需要审批"开关与「访问验证」列。

      **实测**（27 项授权闭环 + 18 项审批属性 + 7 项回归，全通过）：
      需审批绑定在无通行证时判定为"需要审批"且运维侧可见并标记；
      工单审批产生 `pass` 后可访问；**撤销审批后绑定仍然保留**并回到"需要审批"；
      免审批绑定直接放行（默认行为不变）；审批属性可在编辑中切换；
      同一维度重复创建仍原地接管（唯一索引收窄后不产生重复绑定）。
      验证过程中发现并修正一处遗漏：`ListBySubject` 有独立的 SELECT 列清单，
      未同步新字段，导致运维侧 `need_approval` 恒为 false（判定层却是对的，
      两者不一致比单一错误更难发现）。

      **实测**（27 项断言全通过）：授权前运维可见资产 0 → 授权后 1 → 回收后 0；
      参数校验（用户/资产/账号不存在、权限全空、失效时间已过）均拒绝并给可读原因；
      重复创建原地接管且日志记 update；运维/审批人读写均 403；
      生效中的授权不允许直接删除记录。

- [x] **缺陷修复（2026-09-20 实机核对后修复，7 项）** —— 均已编译部署并实测
      · **明文口令泄露（安全）**：`CreateAdmins` 把 `[]AdminSpec` 直接序列化，
        于是建三员时的**明文口令**同时进入 ① `POST /setup/admins` 的响应体、
        ② `sys_init_record.detail`（初始化记录表，jsonb 长期留存）。改为不含口令的
        `adminSummary` 安全视图，并新增回归测试
        `service/setup_test.go::TestCreateAdminsResultHasNoPasswordSecret`；
        设备库中已落库的口令键就地清除（全库扫描命中 0）。
      · **僵尸会话与残缺录像**：服务端优雅关闭只停 HTTP，不理会阻塞在目标 pty
        读上的会话 —— 一次重启留下永久 `active` 的会话与 29 字节残缺录像。
        现在 `proxy.Server.Shutdown` 断开在途连接并**等待会话归档完成**
        （WaitGroup 记的是**会话**而不是连接：记连接会提前放行，实测踩到过）；
        管理面另加 `SessionReconciler`，每 30 秒按"节点心跳超时"收尾，
        兜住 SIGKILL / 断电这类来不及优雅关闭的情况。
        实测：重启期间在途会话被正常收尾（closed / remote_closed / sealed，
        录像经 `record-verify` 校验通过），巡检也能收尾离线节点遗留的会话。
      · **登录日志形同虚设**：`audit_login_log` 建表后**没有任何写入方**（实测 0 条）。
        新增 `repo.LoginLogRepo`，在登录成功 / 失败 / 锁定 / 二次认证各分支写入；
        写入失败只记日志、不阻断登录。实测 6 个账号成功登录 + 2 次失败后有 8 条，
        账号不存在时 `user_id` 写 NULL 而不是 0。
      · **托管账号可以没有凭据**：`validateCredentialMode` 对 managed 直接放行，
        能建出"能选不能用"的账号，直到连接时才以 500 报错。现在 managed
        必须提交口令或私钥；`ops.FetchCredential` 的"未配置凭据"改为业务错误码
        `ASSET_4001`（400 + 可读原因），不再落到 500 + unhandled error。
      · **`/system/config` 权限点闲置**：此前只要登录就能读全部配置（含密码服务
        后端、凭据密钥 ID、登录安全参数），而 `system:config:read` 早已定义却没有
        任何路由使用它。现已收敛；运行指标、网口状态、迁移版本仍对登录用户开放
        （排障需要），前端同步按权限显示配置卡片。
      · **安全管理员权限断链**：`system:role:manage` 归 sec_admin，但权限点目录
        接口要求 `system:role:list`，而该权限只授予了 sys_admin ——
        "唯一有权授予角色的角色打不开权限清单"。迁移 `0023` 补齐。
      · **录像回放错误语义**：未封存录像此前返回 500 `SYS_5000`，前端也只能显示
        "录像不可回放"；现拆成 `RECORD_4001`（未封存）/ `RECORD_4002`（校验失败），
        前端展示后端原因与错误码。
